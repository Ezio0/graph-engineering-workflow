## 2. 市场背景与核心问题

软件工程 Agent 已经能生成代码、测试和文档，但用户把一个需求推进到可信结果时，
仍需要反复：

- 澄清目标、范围与验收条件；
- 协调文档、设计、实现、验证和审核；
- 把失败路由回真正负责的环节；
- 检查 Agent 是否在长任务中偏离原始意图；
- 在权限或不可逆动作前重新取得控制。

核心问题不是缺少另一个会写代码的 Agent，而是缺少一个可复用的交付架构：它能
先与人类明确“做什么”，再自主协调“怎么完成”，并只在确实需要人类判断或授权时
中断。

长时间、多节点执行还会产生意图漂移：每个局部产物看似合理，最终结果却偏离
Human Owner 批准的目标、非目标或验收条件。测试通过不能单独证明结果仍忠于
原始意图。

## 3. 目标用户与核心任务

### 3.1 目标用户

目标用户是对软件工程需求、Git 项目和执行结果负最终责任的人，包括个人开发者、
项目负责人和工程负责人。用户需要理解目标项目，但不需要理解 Graph Engineering。

v1 每个任务只有一位 Human Owner。该 Owner 负责确认意图、批准范围变化、授予
新增权限及授权不可逆动作；其他人的消息不能成为正式输入、改变任务意图或提供
授权。

### 3.2 核心 Job to Be Done

> 当我提出一个软件工程需求时，我希望 Codex 或 Hermes 先帮助我把需求明确到可
> 批准的程度，然后自动完成后续标准文档、开发、验证和独立审核，只在意图变化、
> 重大取舍、权限扩大、无法收敛或不可逆动作前找我。

## 4. 产品类别与形态

Graph Engineering Workflow 定位为：

> **本地优先核心、Skill-first 入口的自主软件工程交付架构。**

“本地优先”定义执行与控制边界：Graph State、权限、产物、证据和确定性逻辑位于
用户环境。“Skill-first”定义主要使用入口：用户通过 Codex，或通过 Telegram / Discord
使用 Hermes 中的 Graph Engineering Skill 发起、恢复和查看任务。Skill 负责需求发现
与交互，本地确定性核心负责状态校验、权限、digest、图执行、路由、失效传播和完成
门禁。

v1 不要求用户安装或管理常驻 daemon。没有活跃 runtime 时，系统不继续执行。
任务状态保存在本地，重新进入创建该任务的 runtime 后可以恢复。

底层 Graph 语义保持平台中立，Codex 和 Hermes 复用同一套交付规则，且各自可独立
完成完整流程，但 v1 不在二者之间共享或转移单个任务。

## 5. 产品愿景与 v1 实现切片

### 5.1 长期愿景

建立覆盖完整软件工程的 Graph Engineering 系统：专业 Agent Loops 是可自主收敛
的节点，显式边负责 typed state、依赖、条件路由、信任、回退、汇合和失效传播，
Human 决策和不可逆授权是明确节点。

### 5.2 v1 实现切片

v1 采用一套共享确定性核心和通用交付节点，并为九类软件工程任务定义独立的场景
Profile/子图、必需节点、验证器和完成条件。共享核心用于复用安全与图执行语义，
不能被用来降低任何任务类别的完整支持与发布验收要求。

通用交付骨架是：

```text
需求发现
  → PRD 与 Human Approval
  → Tech Spec / Impact
  → Implementation Plan / Test Plan
  → Implementation Loop
  → Verification
  → Independent Candidate Review
  ├─ 无待执行的不可逆动作 → Completion Gate
  └─ 需要不可逆动作 → Human Action Approval
                       → Authorized Action Execution
                       → Target-state Verification
                       → Completion Gate
```

下游 finding 可以路由回真正负责的上游节点；上游语义变化使受影响的下游结果
失效。因此它仍是真正的执行图，而不是只能向前移动的文档流水线。

九个正式支持的场景 Profile/子图是：

1. 新项目创建与功能交付；
2. Bug 修复；
3. 线上 Hotfix；
4. 重构与技术债治理；
5. 数据库迁移与架构迁移；
6. 依赖升级与安全修复；
7. 性能优化；
8. 发布与运维；
9. 线上事故响应。

这些 Profile 复用核心节点，但可改变节点组合、路由、必需产物、验证器、回滚和
完成条件。例如性能优化必须建立并复验基准；迁移必须强化兼容性与回滚；事故
响应必须验证服务恢复。

Profile 采用三条风险相称路径：

- **完整计划交付**：适用于新项目、较大功能、迁移和重大架构变更；
- **精简计划交付**：适用于范围明确的 Bug、小型重构、依赖升级等低风险任务；
- **紧急处置**：适用于 Hotfix 和事故响应，缩短发现与文档但保留意图、权限、
  验证、回滚和证据底线。

路径由场景、风险和影响共同决定，不与任务类别机械绑定；精简表示减少篇幅与非必要
节点，不表示降低验收、安全或证据门槛。

九类 Profile 都必须完整定义并通过冻结的支持矩阵。每类都必须覆盖正常、边界、
失败恢复、权限拒绝、意图漂移和真实端到端场景；未全部通过的类别不能宣称 v1
支持。实现上不建设九套独立引擎，但验收上不能用共享核心替代逐类证明。

## 6. 核心价值主张

> 在 Human Owner 保留意图和不可逆权限控制的前提下，让 Codex 或 Hermes 从需求
> 澄清开始，自主完成标准文档与开发闭环，并持续证明结果没有偏离获批意图。

用户获得的价值：

- **少协调**：不再手工衔接文档、开发、测试和审核；
- **少监工**：常规问题由 Agent Graph 自动修订和复验；
- **不偏题**：产物与获批意图持续绑定，语义变化会失效下游；
- **能完成**：工作推进到验证后的目标状态，而非停在建议或代码生成；
- **可控制**：必要的人类判断与不可逆动作仍准确返回 Owner；
- **易采用**：通过 Skill 使用，不要求先理解或部署一套工作流平台。

## 7. 人机协作边界

### 7.1 Human-in-the-loop

需求发现和 PRD 保持 Human-in-the-loop，直到目标、范围、非目标、约束和验收条件
不存在实质性歧义。Human Owner 明确批准后冻结 Intent Baseline 和 Authority
Envelope。

### 7.2 默认自主

批准后，Spec、Impact、Plan、Test Plan、Implementation、Verification 和独立
Candidate Review 默认由 Agent Graph 自主完成。

只有以下情况返回 Owner：

- 目标、范围、非目标或验收条件需要改变；
- 权限需要扩大；
- 出现影响安全、隐私、兼容性或长期成本的重大取舍；
- Reviewer 冲突、超过 loop budget 或无法收敛；
- 缺少外部事实、依赖或凭据；
- 即将 commit、push、merge、deploy、release，或向当前任务会话之外的第三方或
  外部系统发送通信。

### 7.3 Runtime 边界

- 每个任务创建时绑定 Codex 或 Hermes；
- 任务只能在所属 runtime 中继续、批准和完成；
- 只有绑定的 Human Owner 能提供正式输入和授权；
- Codex 任务与 Hermes 任务不共享状态或授权；
- runtime 关闭后任务停止推进，重新打开同一 runtime 后从本地状态恢复；
- v1 不承诺后台执行、跨 runtime 接续或自动事件监听。

## 8. 替代方案与差异化

### 8.1 当前替代方案

| 替代方案 | 可解决的问题 | 仍然存在的缺口 |
|---|---|---|
| 人工驱动单体 Coding Agent | 快速生成代码、测试或文档 | 人持续衔接阶段、搬运上下文并判断是否偏题 |
| 多 Agent 群聊或临时委派 | 并行获得多个专业输出 | 职责、状态、路由、信任和失效规则不明确 |
| 线性模板或脚本流水线 | 固化步骤并提高重复性 | 难以按 finding 回到责任节点并确定性失效下游 |
| 通用工作流引擎 | 编排任务、事件和工具 | 缺少软件工程意图、标准产物和可信完成语义 |

### 8.2 不是单体 Coding Agent

产品对从需求发现到验证完成的闭环负责，而不是只优化代码生成。

### 8.3 不是多 Agent 群聊

节点、输入输出、Reviewer、路由、预算和退出条件显式定义，不由 Agent 临时自由
协商产品方向。

### 8.4 不是线性模板

失败能返回责任节点，语义变化能使下游失效，多个专业 Loop 可以独立收敛和汇合。

### 8.5 确定性安全底线

权限、digest、状态转换、loop budget、失效传播和不可逆门禁由脚本或程序控制，
不依赖 LLM 自我约束。Skill 可以被扩展，但不能绕过这些底线。

### 8.6 标准产物但避免形式主义

每个阶段使用符合专业目的的通行结构、证据和独立审核。低风险和紧急任务可以
精简篇幅，不能删除必要语义或可信门槛。

## 9. 产品边界

### 9.1 v1 范围

- 本地优先的确定性核心，以及 Codex Skill 与 Hermes Skill 两个主要入口；
- 单 Owner、单 runtime 任务；
- 共享确定性核心、通用交付节点和九类完整场景 Profile/子图；
- 完整计划、精简计划和紧急处置三条风险相称路径；
- 标准文档、开发、验证和独立审核闭环；
- 本地持久状态与同 runtime 恢复；
- 同一 Owner 的多任务隔离、共享资源冲突检测和受控任务生命周期；
- 确定性权限、digest、路由、预算、失效和完成门禁；
- Git 项目和项目已有工具链；
- 明确授权后的仓库、交付系统和目标环境操作；
- 基于真实任务的最小化产品学习与 PMF 反证。

### 9.2 v1 非目标

- runtime 关闭后的后台持续执行；
- Codex 与 Hermes 之间共享、转移或接续同一任务；
- 常驻 Core Daemon、中心数据库或自动事件监听服务；
- 为九类软件工程任务重复建设九套彼此独立的引擎或平台；
- 软件工程之外的任意业务工作流；
- 多 Owner、多人参与同一任务或企业级集中协作；
- 云端多租户控制面或在线扩展市场；
- OpenClaw runtime adapter；
- 取代 Git、CI、监控、云、数据库或模型服务；
- 修改旧项目或将其作为运行时依赖。

## 10. 成功与 PMF 假设

### 10.1 交付成功

- 用户能从一个需求开始完成澄清、批准、文档、开发、验证和审核；
- PRD 获批后，常规人工协调显著减少；
- 长任务结果仍与 Intent Baseline 一致；
- 无效权限、证据或状态不能推进任务；
- runtime 中断后能够在同一 runtime 安全恢复；
- 无法可信完成时如实停止并说明阻塞，而不是虚假宣告完成。

### 10.2 PMF 假设

产品更可能获得 PMF，如果用户愿意持续复用 Skill、把它用于更重要和更长的任务，
并在不增加缺陷与事故的前提下降低协调、返工和交付时间。

Human 与 Agent 共同收集真实任务中的介入、失败、返工、复用和放弃证据。Agent
主动提出反证与实验，Human Owner 最终批准产品方向变化。产品不能保证 PMF，但
必须尽早识别错误假设。

## 11. 关键假设与风险

| 假设或风险 | 需要验证的证据 |
|---|---|
| Skill 足以成为主要产品入口 | 用户无需管理服务即可稳定完成真实任务 |
| 单 runtime 任务能满足首批用户 | 用户不频繁要求在 Codex 与 Hermes 间接续 |
| 关闭即暂停是可接受的 | 用户更重视简单性，且同 runtime 恢复可靠 |
| 共享核心加九类 Profile 能完整覆盖软件工程范围 | 九类支持矩阵全部通过，且每类完成真实端到端验证 |
| 标准产物不会变成形式主义 | 审核和追踪更快，人工返工下降 |
| 确定性脚本足以守住边界 | 漂移、越权、证据串用和错误完成被可靠阻止 |
| 产品确有 PMF | 用户持续复用并扩大任务重要性，而非试用后放弃 |

## 12. 定位陈述

> 对于希望把软件工程需求可靠推进到完成、但不想持续协调每个 Agent 和交付阶段
> 的个人开发者与工程负责人，Graph Engineering Workflow 是一套本地优先核心、
> Skill-first 入口的自主交付架构。它先由 Codex 或 Hermes 与用户明确需求，再通过
> 可回退、可审核、防意图漂移的 Agent Graph 自动完成标准文档和开发流程，只在
> 必要决定或不可逆操作前返回人类。

简短描述：

> **明确一次需求，让 Agent Graph 自主交付，只在必要时找你。**
