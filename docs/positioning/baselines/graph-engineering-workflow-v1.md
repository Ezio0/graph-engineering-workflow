## 2. 市场背景与机会

软件工程 Agent 已经能够生成代码、测试和文档，也能完成许多局部工程任务。然而，
把一个仍有歧义的目标推进为真实、可验证的软件工程结果，通常仍依赖人类持续完成：

- 澄清产品意图与验收边界；
- 在多个专业 Agent、交付阶段和工具之间搬运上下文；
- 检查常规产物并把问题路由回真正负责的环节；
- 管理权限、风险、发布和其他不可逆动作；
- 判断最终结果是否真正满足原始目标。

随着任务周期变长、参与节点增多、跨仓库和跨环境协作增加，人类协调成本迅速上升，
Agent 也更容易在多轮局部优化中偏离最初意图。市场机会不是再提供一个更会生成
代码的 Agent，而是建立一种可信的自主交付方式：让 Agent 承担常规协调和可逆执行，
同时让人类保留产品方向及不可逆权限控制。

## 3. 目标用户与核心任务

### 3.1 目标用户

首要用户是对软件工程任务的目标、代码库和执行权限负最终责任的 Human Owner，
包括：

- 为个人项目承担产品与工程责任的个人开发者；
- 对一个或多个代码库承担交付责任的项目负责人；
- 对工程结果及目标环境拥有授权权力的工程负责人。

决定用户是否属于目标人群的关键不是组织身份，而是是否对目标、资源和结果拥有
最终责任与授权。

### 3.2 核心 Job to Be Done

当我有一个仍可能存在歧义的软件工程目标时，我希望系统帮助我澄清并冻结意图，
然后在明确权限范围内自主协调专业 Agent、工具和交付阶段，直到目标状态得到可靠
验证；这样我可以专注于“做什么”和实质性取舍，而不必持续监督“每一步怎么做”。

### 3.3 用户必须保留的责任

Human Owner 始终负责：

- 最终确认产品意图；
- 批准会改变目标或边界的决定；
- 授予新增权限；
- 批准不可逆动作；
- 对产品方向和 PMF 做最终价值判断。

## 4. 核心问题

### 4.1 人工协调瓶颈

现有工具通常优化单个环节或单次对话，却没有对从意图发现到真实目标状态的完整
交付负责。人类仍是阶段之间的调度器、上下文中继、常规 Reviewer 和失败路由器，
限制了 Agent 可以可靠承担的任务长度、范围和重要性。

### 4.2 意图漂移

Agent 在长时间、多节点、多轮执行中可能发生意图漂移：每个局部产物看似合理，
最终结果却偏离 Human Owner 批准的目标、范围、非目标或验收条件。测试通过只能
证明某些行为符合测试，不能单独证明交付仍忠于原始意图。

产品因此必须让批准的意图成为贯穿执行图的稳定参照，并能发现偏离、阻止无效结果
继续传播，以及在意图确实需要改变时返回 Human Owner。

### 4.3 可信执行缺口

能够提出建议不等于能够可靠交付。真实软件工程需要管理权限、外部副作用、失败
恢复、独立审核、证据有效性和目标环境验证。缺少这些机制，Agent 要么停在代码或
方案 Candidate，要么以不可接受的风险换取自动化。

## 5. 产品类别

Graph Engineering Workflow 定位为：

> **本地优先的自主软件工程交付系统。**

它不是单纯的 Coding Agent、聊天机器人、文档流水线或通用工作流引擎。它把能够
自主收敛的专业 Agent Loops 作为执行节点，把依赖、状态传递、条件路由、信任、
回退、汇合和失效传播建模为显式边，并把 Human 决策与不可逆授权建模为明确的图
节点。

底层图模型保持领域中立，但 v1 的产品能力、内置路径、文档、测试、兼容保证和
官方支持严格限定在软件工程。

## 6. 价值主张

### 6.1 核心价值主张

在 Human Owner 保留产品意图与不可逆权限控制的前提下，以尽可能少的人类协调，
把软件工程目标自主推进到经过验证的真实目标状态，并持续证明交付没有偏离获批
意图。

### 6.2 用户价值

- **减少协调**：系统负责常规阶段衔接、上下文传递、失败路由和重复审核。
- **保持意图**：长时间、多 Agent 执行持续绑定 Human Owner 批准的目标。
- **完成真实工作**：在明确授权后实际操作仓库、交付系统和目标环境，而不只生成
  建议或代码。
- **保留控制**：意图变化、权限扩张、重大取舍和不可逆动作准确返回人类。
- **可信完成**：结果通过验证、独立审核和证据链证明，而不是由 Agent 自我宣告。
- **降低接入成本**：内置软件工程交付图可开箱使用，高级用户仍可扩展。

## 7. 当前替代方案

目标用户目前通常组合使用以下替代方案：

| 替代方案 | 能解决什么 | 仍然存在的缺口 |
|---|---|---|
| 单体 Coding Agent | 代码生成、修改和局部验证 | 仍需人类协调完整生命周期，长期意图保持有限 |
| 多 Agent 群聊或临时委派 | 并行获得不同专业输出 | 职责、状态、路由、信任和失效规则不明确 |
| 线性文档/CI 流水线 | 阶段顺序和确定性自动化 | 难以表达自主循环、条件分支、回退和语义失效 |
| 通用工作流引擎 | 编排任务、事件和工具 | 缺少软件工程意图发现、专业产物和可信交付语义 |
| 人工项目管理与工程协调 | 灵活处理复杂情况 | 成本高、吞吐受限，人类成为持续调度瓶颈 |
| 自建脚本与 Agent 组合 | 针对单一团队高度定制 | 难以复用，安全、审计和跨 runtime 一致性需重复建设 |

这些是产品定位中的替代方案类别，并非对具体厂商产品作功能或市场份额判断。

## 8. 差异化与可防御性

### 8.1 真正的 Graph Engineering

节点是可执行、可自主收敛并接受独立审核的专业 Agent Loop，或确定性控制节点；
不是把 PRD、Spec、代码等产物标签重新命名为“节点”。边显式描述 typed state、
依赖、路由条件、信任要求、回退、汇合和失效行为。

### 8.2 Intent Baseline 驱动

批准的意图不是一次性提示词，而是带版本、可验证绑定、能使下游结果失效的执行
基线。产品在整个任务生命周期中防止 Agent 用局部合理性掩盖整体偏离。

### 8.3 确定性安全内核

权限、验证、digest 绑定、状态归约、loop budget、路由和不可逆边界由确定性逻辑
控制，不交给 LLM 自由解释。高级用户只能收紧规则，不能通过自定义 Graph 绕过
底线。

### 8.4 从意图到真实状态的证据闭环

系统不把生成文档或代码视为默认终点。任务终点由 Human Owner 声明的目标决定，
并要求产物、验证、独立审核、授权和外部副作用形成可追踪、可恢复、不可串用的
证据链。

### 8.5 产品优先、框架开放

普通用户使用内置软件工程图，不必先学习或设计 Graph；高级用户可以扩展节点、
边、策略和 runtime adapter。扩展能力扩大适用性，但不改变产品对可靠完成的统一
承诺。

### 8.6 多入口、单一事实

Codex 与 Hermes 是 v1 的完整入口，可以独立使用并跨入口接续同一任务。核心图
语义和持久化状态不归属于某个聊天界面，为未来 runtime 扩展保留平台中立边界。

## 9. 产品原则

1. **可靠性优先于自主率**：无法证明完成时保持未完成。
2. **意图优先于局部优化**：Agent 不得自行合理化对批准目标的改变。
3. **默认自主，异常升级**：人类关注实质性决定，而非常规过程确认。
4. **权限与副作用显式化**：紧急性不能成为绕过授权的理由。
5. **标准产物服务决策**：每个阶段遵循专业目的和质量契约，不机械堆砌文档。
6. **可恢复、可审计**：任何结果都能追溯到输入、运行、验证、审核和授权。
7. **本地掌握控制权**：状态、凭据、权限和证据默认留在用户环境中。
8. **数据与逻辑分离**：用户、项目和环境差异通过配置表达，不进入通用引擎逻辑。
9. **平台中立**：Codex、Hermes 及未来平台通过 runtime adapter 接入。
10. **诚实面对反证**：产品学习主动寻找没有 PMF 或无法可靠交付的证据。

## 10. 产品边界

### 10.1 v1 范围

v1 服务完整的软件工程任务，包括新项目与功能交付、Bug、Hotfix、重构、迁移、
依赖与安全升级、性能优化、发布运维和事故响应。各类别都必须具有真实、可执行且
经过验收的内置路径，不能只做到理论可表达。

产品支持从零创建项目和原地接入既有项目，可跨多个 Git 仓库、服务和运行环境；
在 Human Owner 明确授权后，可以实际执行所需操作。具体功能、平台、集成、权限
和发布矩阵要求由 PRD 定义。

### 10.2 交互与所有权边界

- v1 是本地优先、严格单 Owner 的产品；
- Codex 与 Hermes 是正式支持的完整入口；
- Human Owner 可以同时运行多个隔离任务；
- 外部事件可以触发只读诊断，但不能自动获得写权限；
- 普通用户无需理解 Graph Engineering，高级用户可在软件工程范围内自定义。

### 10.3 非目标

- 软件工程之外的任意业务工作流或通用知识图谱；
- 多 Owner、多人参与同一任务或企业级集中协作；
- 云端多租户控制面、在线扩展市场和商业分发生态；
- 面向非技术用户的无代码工作流产品；
- 取代 Git、CI、监控、告警、工单、云、数据库或模型服务；
- 穷举所有厂商、技术栈或版本控制系统；
- 在 v1 正式支持 OpenClaw；
- 保证任何任务必然解决或保证产品必然获得 PMF；
- 修改旧项目或将其作为运行时依赖。

## 11. 成功定义与 PMF 假设

### 11.1 交付成功

产品成功完成一次任务意味着：

- Human Owner 声明的目标状态得到可靠验证；
- 最终结果与获批意图保持一致；
- 常规人工协调显著减少；
- 实质性变化、异常和权限边界准确升级；
- 全过程可恢复、可审计，证据完整且不可串用；
- 无法可信完成时安全停止，如实说明阻塞、证据缺口和回滚状态。

### 11.2 产品成功假设

产品将更可能获得 PMF，如果目标用户：

- 在真实软件工程任务中持续复用，而非试用后弃用；
- 逐步把产品用于更多类别、更长周期和更重要的任务；
- 在不增加缺陷或事故的前提下，明显减少协调、返工和交付时间；
- 愿意授权系统实际执行，而不只把它当作建议或代码生成工具；
- 认为意图保持、可靠恢复和证据闭环足以支持更高信任。

### 11.3 Human 与 Agent 的共同责任

Human 与 Agent 共同负责提高获得 PMF 的概率，并尽早发现反证：

- Agent 从真实任务中整理人工介入、失败、返工、节省时间、复用和放弃原因；
- Agent 主动提出假设、反证和建议实验，而不是只证明既有方向；
- Human Owner 对价值、取舍和产品方向做最终判断与批准；
- 产品达到可用阶段后，逐步用自身交付自身的真实软件工程任务；
- 任何对外共享产品学习数据的动作必须单独授权。

该机制服务本产品的持续发现，不把 v1 扩张为通用市场研究平台。具体指标、基线和
测量方式由 PRD 定义。

## 12. 关键假设与待验证证据

| 假设 | 需要的证据 | 反证信号 |
|---|---|---|
| 用户的主要瓶颈是跨阶段协调，而非单纯代码生成能力 | 人工介入与上下文搬运显著下降 | 用户仍需持续监督每个步骤 |
| Intent Baseline 能降低长任务偏离 | 漂移被提前识别，最终验收偏差下降 | 基线增加文档负担但不能阻止偏离 |
| 用户愿意在明确门禁下授权实际执行 | 从建议模式逐步转向仓库和环境操作 | 用户长期只消费建议，不授权执行 |
| 内置图能降低采用成本 | 新用户无需自定义即可完成真实任务 | 用户必须先设计大量 Graph 才能使用 |
| 单 Owner、本地优先足以找到首批 PMF | 个人开发者和工程负责人持续复用 | 核心价值只有多人或云端场景才能成立 |
| 标准化产物提升可信度而非制造形式主义 | 审核和追踪更快，返工下降 | 文档增加但决策质量和交付可靠性不变 |
| Codex 与 Hermes 双入口带来持续性价值 | 跨入口接续被真实使用 | 用户只需要一个入口，双适配拖累核心体验 |

## 13. 主要定位风险

| 风险 | 定位影响 | 应对原则 |
|---|---|---|
| v1 软件工程范围过宽 | 产品无法对每类任务建立可信承诺 | 以冻结且全部通过的支持矩阵约束发布声明 |
| “Graph Engineering”难以被普通用户理解 | 类别价值被技术术语掩盖 | 对外先讲自主交付结果，图细节按需展开 |
| 标准产物退化为文档形式主义 | 增加成本却不提升可靠性 | 采用风险相称的质量契约，不以篇幅衡量完整性 |
| 安全门禁造成体验摩擦 | 用户认为产品仍需频繁监督 | 只在实质性与不可逆边界中断，并提供完整决策包 |
| 本地、单 Owner 限制市场规模 | 无法覆盖企业多人协作需求 | 先验证首批核心价值，不在 v1 提前建设企业平台 |
| 多 runtime 适配分散资源 | 核心执行能力成熟变慢 | 共享核心语义和状态，adapter 不拥有通用逻辑 |
| 产品完成但缺乏 PMF | 技术成功无法转化为持续使用 | 真实任务、自用、持续复用和反证驱动发现 |

## 14. 定位陈述

### 14.1 标准定位陈述

> 对于需要对软件工程目标、代码库和执行结果负责的个人开发者与工程负责人，
> Graph Engineering Workflow 是一个本地优先的自主软件工程交付系统。它在
> Human Owner 保留意图和不可逆权限控制的前提下，协调多个专业 Agent Loops，
> 将模糊目标推进到经过验证的真实结果。不同于单体 Coding Agent、临时多 Agent
> 群聊或线性文档流水线，它通过显式执行图、Intent Baseline、确定性安全内核、
> 独立审核和证据闭环减少人工协调，并防止长时间执行中的意图漂移。

### 14.2 简短描述

> **让 Agent 自主完成软件工程交付，同时让结果始终忠于人类批准的意图。**

## 15. 已确认的定位决策

1. 建设独立新项目，不修改旧项目，也不将旧项目作为运行时依赖；
2. 使用真正的 Graph Engineering，而不是把线性产物流程重新命名为图；
3. Positioning 与 PRD 保持 Human-in-the-loop，直到实质性歧义消除；
4. PRD 获批后，可逆工作由 Agent Graph 默认自主完成；
5. 可靠性优先，并持续防止意图漂移；
6. v1 覆盖完整软件工程，底层图模型领域中立，官方支持不扩张到任意业务流程；
7. 产品优先、框架开放，扩展不能绕过确定性安全内核；
8. 产品本地优先、严格单 Owner；
9. Codex 与 Hermes 是 v1 的完整入口，OpenClaw 不在 v1；
10. 在明确授权后，系统要实际操作仓库、交付系统和目标环境；
11. 每个阶段的产物遵循业内通行的专业结构、质量契约与追踪要求；
12. Human 与 Agent 共同提高获得 PMF 的概率并主动识别反证。
