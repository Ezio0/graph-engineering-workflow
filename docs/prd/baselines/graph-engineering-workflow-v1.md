## 2. 产品摘要

Graph Engineering Workflow 是一个本地优先、单 Owner、可靠性优先的自主软件
工程交付系统。Human Owner 通过 Codex 或 Hermes 描述目标并批准意图与权限；
多个专业 Agent Loops 随后通过显式执行图，自主推进已授权的可逆工作，直到真实
目标状态得到验证。

产品解决两个核心问题：

1. 从模糊目标到真实结果之间仍需要人类反复协调阶段、Agent、工具、审核和返工；
2. Agent 在长时间、多节点迭代中可能发生意图漂移，使局部正确的结果偏离获批
   目标。

产品的核心承诺是：**减少常规人工协调，同时持续证明最终结果忠于 Human Owner
批准的意图。**

## 3. 用户与待完成任务

### 3.1 核心用户

核心用户是对软件工程任务的目标、Git 项目和执行权限负最终责任的 Human Owner，
包括个人开发者、项目负责人和工程负责人。用户需要理解软件工程、Git 和目标
项目，但无需理解 Graph Engineering。

每个任务严格绑定一位 Owner。只有该 Owner 可以提供正式输入、批准基线、扩大
权限及授权不可逆动作。其他人不能参与该任务；独立审核由 Agent Reviewer 完成。

### 3.2 Jobs to Be Done

| ID | Job to Be Done |
|---|---|
| JTBD-01 | 当目标仍有歧义时，帮助我形成可批准、可验证的明确意图 |
| JTBD-02 | 意图获批后，自主协调 Agent、阶段和工具，减少我的常规介入 |
| JTBD-03 | 在长时间、多节点执行中持续防止结果偏离获批意图 |
| JTBD-04 | 经明确授权后实际操作仓库和环境，并验证真实目标状态 |
| JTBD-05 | 失败、中断或取消后保留真实状态，安全恢复、继续或回滚 |
| JTBD-06 | 从真实使用中识别产品价值、错误假设和 PMF 反证 |

## 4. 产品目标与成功指标

### 4.1 v1 目标

| ID | 目标 |
|---|---|
| G-01 | 通过 Codex 或 Hermes 以自然语言发起并完成软件工程任务 |
| G-02 | 冻结清晰、版本化、可验证的 Intent Baseline 与 Authority Envelope |
| G-03 | 自主完成获批范围内的可逆交付，并准确升级异常和不可逆边界 |
| G-04 | 防止意图漂移、越权、证据串用及无效结果向下游传播 |
| G-05 | 每个阶段产出符合专业目的、可审核、可追踪的标准文档或证据 |
| G-06 | 只在真实目标状态、验收条件、验证和独立审核均通过时完成任务 |
| G-07 | 用真实任务数据支持 Human 与 Agent 共同提高获得 PMF 的概率 |

### 4.2 成功指标框架

发布前先建立基线，具体数值目标由 Human Owner 根据真实数据批准，不在引擎中
硬编码任意阈值。

| 维度 | 指标方向 |
|---|---|
| 可靠交付 | 目标状态验证率和验收通过率提升；未发现意图偏离下降 |
| 人类负担 | 常规介入、上下文搬运、人工返工协调和交付耗时下降 |
| 安全 | 未授权动作、无效授权复用和证据串用必须为零 |
| 恢复 | 状态完整恢复；非幂等副作用重复必须为零 |
| PMF | 持续复用、任务类别扩展、任务重要性和实际执行授权意愿提升 |
| 负面信号 | 主动放弃、只使用建议模式、产品导致的缺陷或事故下降 |

## 5. 范围与优先级

### 5.1 Must — v1 发布必需

- 九类内置软件工程路径：
  1. 新项目创建与功能交付；
  2. Bug 修复；
  3. 线上 Hotfix；
  4. 重构与技术债治理；
  5. 数据库迁移与架构迁移；
  6. 依赖升级与安全修复；
  7. 性能优化；
  8. 发布与运维；
  9. 线上事故响应。
- 新项目创建及既有 Git 项目原地接入；
- Codex 和 Hermes 两个可独立使用、可跨入口接续的完整入口；
- 完整、精简和紧急三类风险相称路径；
- 意图冻结、自主执行、权限门禁、独立审核、验证和证据链；
- 状态持久化、恢复、冲突处理、暂停、取消、撤权和受控回滚；
- 人工发起及外部事件触发的只读诊断；
- 全阶段标准产物、质量门槛和需求追踪；
- 本地安装、升级、状态迁移和最小化 PMF 学习记录。

### 5.2 Should — v1 应提供

- 高级用户本地扩展节点、边、策略和 runtime adapter；
- 常见 Git 托管、CI、监控、数据库和云工具的示例 adapter；
- 产品学习记录的本地导出和对比。

### 5.3 Won't — v1 不做

- 软件工程之外的任意业务工作流；
- 多 Owner 或其他人参与同一任务；
- 云端多租户控制面、企业集中管控或在线扩展市场；
- 面向非技术用户的无代码产品；
- 非 Git 版本控制系统；
- OpenClaw runtime adapter；
- Windows 原生兼容承诺；
- 完全离线保证；
- 穷举所有厂商与技术栈集成；
- 自动获得不可逆动作权限；
- 修改旧项目或将其作为运行时依赖。

### 5.4 运行与集成边界

v1 正式支持 macOS 和 Linux，Windows 可通过 WSL 使用。最低开箱能力为本地文件
系统、Shell、Git、Codex、Hermes，以及读取项目规范并执行项目已有工程命令。

产品对语言和技术栈保持中立。Git 托管、CI、云、数据库和监控等厂商能力通过
命令、连接器或 adapter 接入；缺少能力时必须明确标记阻塞或“未验证”。

## 6. 用户故事

| ID | 用户故事 | 核心验收 |
|---|---|---|
| US-01 | 作为 Owner，我希望创建新项目或原地接入既有 Git 项目，以免迁移目录、工具链或开发方法 | 读取规范、Git 状态、工具和验证能力；只问关键缺口；只读发现不产生写权限 |
| US-02 | 作为 Owner，我希望只描述目标，由系统识别任务、目标状态、资源、风险和歧义，以免先设计 Graph | 批量提问并给出建议；自动选择完整、精简或紧急路径；允许高级用户覆盖 |
| US-03 | 作为 Owner，我希望批准清晰的目标与权限摘要，以便知道系统会做什么及不做什么 | 摘要覆盖目标、范围、非目标、验收、资源、权限、风险和缺口；批准绑定当前内容；普通聊天不算批准 |
| US-04 | 作为 Owner，我希望批准后系统持续推进可逆工作，以免逐步确认和搬运上下文 | 普通失败自动修订复验；只在意图、权限、重大选择、外部阻塞、不收敛或不可逆边界暂停 |
| US-05 | 作为 Owner，我希望产物与决定持续绑定获批意图，以免局部合理累积成整体偏离 | 偏离时阻止传播并展示证据；先在原意图内修正；语义变化重新批准并失效下游 |
| US-06 | 作为 Owner，我希望只授权明确动作和资源，以便系统实际执行但不能扩大或复用权限 | 不可逆动作分别授权；绑定动作、资源、状态 digest、影响、验证、回滚和有效期 |
| US-07 | 作为 Owner，我希望任务在崩溃、重启或断网后恢复，以免丢失或重复副作用 | 展示中断点、动作、权限、副作用和下一步；不静默重做非幂等动作 |
| US-08 | 作为 Owner，我希望阻止不安全并发，并能暂停、取消或撤权，以免任务互相破坏 | 冲突隔离、排队或升级；取消不伪装成回滚；新增风险或权限的回滚重新授权 |
| US-09 | 作为 Owner，我希望外部事件自动触发诊断，以便尽快获得证据而不自动写入 | 无人时只读；通知含影响、置信度、证据、建议和权限；重复告警去重 |
| US-10 | 作为 Owner，我希望在 Codex、Telegram 或 Discord 间接续任务，以免入口变化影响事实 | Codex/Hermes 均可独立完成；共享状态、授权和证据；无隐藏状态 |
| US-11 | 作为 Owner，我希望每阶段有专业标准产物，以便独立审阅并追踪需求到结果 | 满足第 8.1 节契约；精简路径仍保留意图、权限、验证、审核、证据和追踪 |
| US-12 | 作为 Owner，我希望完成摘要证明目标状态，而非只罗列产物 | 目标、验收、项目门槛、审核和 digest 均通过；列明变化、证据、遗留、副作用和回滚 |
| US-13 | 作为 Owner，我希望证据最小化并脱敏，以免敏感信息因审计或模型调用扩散 | 凭据不入证据；泄露触发隔离和不复述秘密的报告；外发需单独授权 |
| US-14 | 作为高级用户，我希望配置和扩展软件工程 Graph，以适配项目而不破坏可信底线 | 数据值位于配置；扩展声明输入输出、权限、副作用、失败和验证语义；加载前校验；底线不可关闭 |
| US-15 | 作为 Owner，我希望系统总结真实使用价值和反证，以免把功能完成误认为 PMF | 本地记录最小化的介入、返工、耗时、失败、复用和放弃；Agent 提出反证和实验；方向由 Owner 批准 |

## 7. 关键用户旅程

| 场景 | 发现路径 | 目标终点 |
|---|---|---|
| 计划内功能或重大架构变更 | 完整 Positioning/PRD | 由 Owner 声明，可包含部署与环境验证 |
| 普通 Bug、升级或小型重构 | 精简基线 | 通过修复、回归和独立审核的目标状态 |
| Hotfix 或事故响应 | 紧急基线：影响、止损、权限、验证、回滚 | 服务恢复、验证完成、副作用与复盘证据记录 |
| 跨仓库迁移或发布 | 完整或精简路径，按风险决定 | 所有目标仓库、服务和环境完成协调验证 |
| 自动事件触发 | 无人时只读诊断 | 诊断建议，或 Owner 批准后的实际处置结果 |

无论采用哪条路径，都不得省略明确意图、权限边界、验证、独立审核和证据链。

## 8. 产品需求

| ID | 优先级 | 需求与核心验收 |
|---|---|---|
| PR-01 | Must | **项目与任务管理：**稳定任务 ID、单 Owner 绑定、搜索/查看/暂停/恢复/取消/归档；支持新项目、既有项目、单仓库和多仓库 |
| PR-02 | Must | **发现与基线：**自然语言发起、风险相称发现、明确批准、版本化 Intent Baseline 和 Authority Envelope |
| PR-03 | Must | **Graph 执行：**支持专业 Loops、确定性控制节点、依赖、路由、并行、汇合、回退、重试、预算和失效传播 |
| PR-04 | Must | **意图保持：**节点输入、产物、验证和审核绑定当前基线；偏离阻断；语义变更重新批准并失效下游 |
| PR-05 | Must | **授权：**最小权限、动作级授权、身份/资源/状态/有效期绑定；不可逆动作独立授权且不可跨状态复用 |
| PR-06 | Must | **持久化与恢复：**重要转换可重放；崩溃恢复不丢状态、不重复非幂等副作用 |
| PR-07 | Must | **冲突与回滚：**执行前检测共享资源冲突；取消、撤权和回滚如实处理外部副作用 |
| PR-08 | Must | **事件触发：**支持人工及 CI/监控/安全事件；无人时只读；事件去重；不取代来源系统 |
| PR-09 | Must | **完整入口：**Codex 和 Hermes 分别可完整使用，并共享可跨入口接续的单一任务事实 |
| PR-10 | Must | **标准产物：**每阶段具备标准结构、版本、输入基线、责任节点、独立审核、退出条件和端到端追踪 |
| PR-11 | Must | **证据与隐私：**证据本地、最小化、脱敏、digest 绑定；敏感信息事故触发隔离与报告 |
| PR-12 | Must | **可信完成：**只有目标状态、验收、项目门槛、审核和证据全部有效时才能完成 |
| PR-13 | Must | **安装与升级：**macOS/Linux 本地安装、初始化、备份、升级、版本迁移和失败恢复 |
| PR-14 | Must | **产品学习：**本地最小化 PMF 数据、反证分析、实验建议和 Owner 方向批准 |
| PR-15 | Should | **高级扩展：**本地安装并校验自定义节点、边、策略和 adapter；运行时仍受安全内核约束 |

### 8.1 标准阶段产物契约

“标准”表示符合该专业阶段的通行信息结构和决策目的，不表示固定篇幅或机械套用
模板。

| 阶段 | 最低必备内容 |
|---|---|
| Positioning | 背景、用户、问题、类别、价值主张、替代方案、差异化、边界、成功假设、风险、定位陈述、批准状态 |
| PRD | 文档控制、问题、用户、JTBD、User Stories、目标与指标、范围、旅程、需求与验收、风险依赖、发布门槛、追踪、批准状态 |
| Tech Spec | 架构上下文与决策、组件、状态与数据、接口、流程、安全、可靠性、可观测性、迁移回滚、替代方案、需求追踪 |
| Impact Analysis | 受影响模块/用户/数据/依赖、兼容性、安全隐私、运行成本、迁移回滚、风险、ADR 判断 |
| ADR | 背景、约束、候选方案、取舍、决定、后果、状态、失效条件 |
| Implementation Plan | 工作分解、依赖顺序、责任节点、交付物、风险、检查点、退出条件、需求映射 |
| Test Plan | 范围、策略、追踪、环境数据、正常/边界/失败/恢复/安全场景、自动化层级、通过标准、证据 |
| Implementation | 符合项目规范的代码、配置、迁移与必要文档；可追踪且不夹带未批准范围 |
| Verification Report | 构建测试、静态/安全/性能检查、目标状态、证据、偏差、遗留问题和残余风险 |
| Candidate Review | 独立 Reviewer、输入、逐项需求结论、发现严重级别、意图与证据完整性、发布建议 |
| Completion Record | 实际变化、目标状态、授权、副作用、部署/发布结果、回滚、遗留事项、审计入口 |

所有产物必须声明状态、版本、输入基线、责任节点和审核结论；关键结论必须有证据
或标记为假设；上游语义变化必须使受影响产物失效。内部执行日志不能代替正式
产物，缺少必备内容或独立审核时阶段不得完成。

## 9. 确定性安全底线

以下能力不能被 LLM、自定义 Graph、配置或 runtime adapter 绕过：

- Authority Envelope 和动作级权限校验；
- Intent Baseline、状态、产物、证据和审核的 digest 绑定；
- 状态归约、边条件、loop budget 和不可逆门禁；
- 资源冲突检测与副作用幂等保护；
- 上游语义变化触发的下游失效传播；
- 阶段质量门槛、目标状态和证据有效性判定。

LLM 可以发现语义问题并提供判断材料，但权限执行、版本绑定、状态失效和完成判定
必须由确定性逻辑控制。高级用户只能收紧安全规则，不能降低底线。

## 10. 非功能需求

| ID | 要求 |
|---|---|
| NFR-01 可靠性 | 验证、证据或审核不足时保持未完成，安全停止并解释下一步 |
| NFR-02 可恢复性 | 状态转换可追溯；恢复不丢失基线、权限、历史或证据绑定 |
| NFR-03 平台中立 | 通用图语义不依赖 Codex、Hermes 或具体厂商 |
| NFR-04 数据逻辑分离 | 拓扑、策略、阈值、命令、路径、端口、偏好和环境值来自配置或数据 |
| NFR-05 隐私与权限 | 最小权限、最小留存、透明外发；联网不等于允许任意发送数据 |
| NFR-06 可用性 | 普通用户无需理解 Graph 内部；批准和升级信息清晰且不可误解 |
| NFR-07 可审计性 | 从意图到结果可追踪、可重放，证据不可跨任务、基线或 Candidate 串用 |
| NFR-08 兼容性 | 遵循既有项目规范和工具链；能力缺失时明确报告 |

## 11. 依赖、约束与风险

### 11.1 依赖与约束

- 用户环境具有 Git、本地文件系统、Shell 和项目工程工具；
- 至少安装 Codex 或 Hermes 其中一个完整 runtime adapter；
- 外部动作依赖相应连接器、凭据、网络和 Owner 权限；
- Graph State、凭据、权限和证据由本地控制；
- 旧项目仅作只读背景参考，不能修改或成为运行时依赖。

### 11.2 主要风险

| 风险 | 产品级缓解 |
|---|---|
| 九类任务范围过宽 | 发布前冻结支持矩阵；未全部通过的范围不得宣称支持 |
| 意图漂移 | 基线绑定、偏离检测、独立审核和确定性失效传播 |
| 未授权副作用 | 最小权限、动作级授权、状态 digest 和有效期 |
| 文档形式主义 | 风险相称的产物契约，以决策和证据质量而非篇幅判断 |
| Codex/Hermes 状态分叉 | 共享持久化状态和核心语义，adapter 不拥有隐藏事实 |
| 扩展破坏安全 | 加载校验与不可绕过的运行时安全内核 |
| 敏感数据扩散 | 最小留存、脱敏、隔离和泄露响应 |
| 技术完成但没有 PMF | 真实任务、自用、持续复用和反证驱动的产品发现 |

## 12. v1 发布门槛

发布前必须冻结九类任务的支持矩阵。每类必须覆盖：

- 内置端到端正常路径与关键边界；
- 失败后的自动修订和重新验证；
- 权限拒绝、过期和 digest 失配；
- 意图漂移检测及下游失效；
- 取消、崩溃恢复或回滚；
- 标准阶段产物和独立审核；
- Candidate Review、目标状态和证据链验收。

冻结矩阵中的全部必选场景和验收条件必须通过，不得在发布时临时缩小范围。每类
还必须至少在一个真实项目和真实工具链中完成端到端验证，作为模拟、单元和集成
测试之外的真实性下限。未经验证的技术栈或厂商集成必须明确标记。

此外必须满足：

- Codex 与 Hermes 各自独立完成代表性任务，并通过跨入口接续测试；
- 未授权动作、无效授权复用、证据串用和非幂等副作用重复均为零；
- 敏感信息默认不进入证据，模拟泄露能够触发隔离和报告；
- Owner 可仅用自然语言发起，并在不理解 Graph 内部的情况下完成任务；
- 最终摘要证明真实目标状态，而非只罗列产物。
