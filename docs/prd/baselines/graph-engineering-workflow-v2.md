## 2. 产品摘要

Human Owner 在 Codex 或 Hermes 中调用 Graph Engineering Skill，描述一个软件
工程需求。Skill 先帮助 Owner 明确目标、范围、非目标、约束和验收条件；本地
确定性核心保存并执行 Graph State、权限和证据规则。Owner 批准 PRD 后，Agent
Graph 自动完成标准文档、开发、验证和独立 Candidate Review，仅在意图变化、
权限扩大、重大取舍、无法收敛、外部阻塞或不可逆动作前中断。

在 Owner 授权后，系统实际操作获批的仓库、交付系统或目标环境，并验证真实目标
状态；任务不会停在操作建议或未执行的计划上。

每个任务绑定创建它的 runtime。runtime 关闭后任务停止推进；重新进入同一 runtime
后从本地持久状态恢复。Codex 与 Hermes 复用相同图语义，但不共享单个任务。

## 3. 用户、JTBD 与产品目标

### 3.1 核心用户

核心用户是对软件工程需求、Git 项目和执行结果负最终责任的 Human Owner，包括
个人开发者、项目负责人和工程负责人。每个任务只有一位 Owner。

### 3.2 Jobs to Be Done

| ID | Job to Be Done |
|---|---|
| JTBD-01 | 把一个仍有歧义的需求澄清为可批准、可验证的意图 |
| JTBD-02 | 批准后自动完成标准文档和开发流程，减少常规协调 |
| JTBD-03 | 在多节点、多轮执行中阻止意图漂移和无效结果传播 |
| JTBD-04 | 经授权后实际操作仓库和环境、验证真实目标状态，并只在必要边界中断我 |
| JTBD-05 | runtime 中断后，在同一 runtime 中安全恢复任务 |
| JTBD-06 | 从真实使用中识别产品价值、错误假设和 PMF 反证 |

### 3.3 v1 目标

| ID | 目标 |
|---|---|
| G-01 | Codex 或 Hermes 用户可通过 Skill 从需求开始完成端到端交付 |
| G-02 | PRD 批准后冻结 Intent Baseline 与初始 Authority Envelope，标准文档与开发节点默认自主运行 |
| G-03 | 意图、权限、状态、产物、证据和审核保持可验证绑定 |
| G-04 | 常规失败自动回到责任节点，只有必要边界升级给 Owner |
| G-05 | runtime 关闭时安全停止，同一 runtime 重启后可恢复 |
| G-06 | 真实目标状态、验收、验证和独立审核全部通过后才完成 |
| G-07 | 用最小化真实数据检验产品价值和 PMF 假设 |
| G-08 | 九类软件工程任务均具有完整 Profile/子图并通过冻结支持矩阵 |

### 3.4 成功指标框架

| 维度 | 成功方向 |
|---|---|
| 可靠交付 | 目标状态与验收通过率提升；未发现的意图偏离下降 |
| 人类负担 | PRD 批准后的常规介入、上下文搬运、返工协调和交付耗时下降 |
| 安全与恢复 | 未授权动作、证据串用和非幂等重复为零；同 runtime 恢复完整 |
| 九类覆盖 | 冻结支持矩阵的全部必选场景通过；此外每类至少完成一个真实端到端场景 |
| PMF | 持续复用、任务类别扩展、任务重要性和实际执行授权意愿提升 |

具体数值在真实任务建立基线后由 Human Owner 批准，不把未经验证的阈值硬编码进
确定性核心。

## 4. v1 范围

### 4.1 Must

- Codex 与 Hermes 各自提供完整的 Graph Engineering Skill 体验；Hermes v1 通过
  Telegram 或 Discord 与 Owner 交互；
- 每个任务创建时绑定一个 runtime 和一位 Human Owner；其他人的消息不能进入任务
  状态、改变意图或提供授权；
- 从零创建项目和原地接入既有 Git 项目，并支持跨多个仓库、服务和环境的任务；
- 自然语言需求发现与 PRD 明确批准；
- 一套共享确定性核心和通用交付节点；
- 九类软件工程场景 Profile/子图及各自必需节点、验证器、回滚与完成条件；
- 完整计划、精简计划和紧急处置三条风险相称路径；
- 标准的 Spec、Impact、Plan、Test Plan、Implementation、Verification 和
  Candidate Review；
- 自动修订、重新审核、finding 回路和上游失效传播；
- 本地持久状态、同 runtime 恢复及非幂等副作用保护；
- 多任务隔离、共享资源冲突检测、暂停、取消、撤权、归档和受控回滚；
- 本地安装、升级、版本迁移和失败恢复；
- 确定性 Authority、digest、schema、路由、loop budget 和完成门禁；
- 明确授权后的仓库、交付系统和目标环境操作；
- 最小化、脱敏的证据与产品学习记录。

### 4.2 Should

- 高级用户配置图、策略、模板和验证器；
- 复用项目已有 Skills、命令和连接器；
- 常见 Git 托管、CI、监控、数据库和云能力的示例 adapter。

### 4.3 Won't

- runtime 关闭后继续后台执行；
- Codex 与 Hermes 共享、转移或接续同一任务；
- 常驻 daemon、中心数据库或自动事件监听；
- 为九类任务重复建设九套彼此独立的引擎或平台；
- 多 Owner 或其他人参与同一任务；
- 软件工程之外的任意业务工作流；
- 云端多租户控制面、在线扩展市场或 OpenClaw adapter；
- 非 Git 版本控制系统；
- 自动获得 commit、push、merge、deploy、release，或向当前任务会话之外发送
  第三方和外部系统通信的权限；
- 修改旧项目或将其作为运行时依赖。

### 4.4 九类正式支持范围

| 场景 Profile/子图 | 必须具备的类别级完成语义 |
|---|---|
| 新项目创建与功能交付 | 项目或功能目标、验收、回归验证，以及 Owner 声明的目标环境状态 |
| Bug 修复 | 可验证的问题复现、责任边界、修复、回归测试和无关行为保护 |
| 线上 Hotfix | 影响与止损目标、最小安全变更、生产验证、回滚条件和副作用记录 |
| 重构与技术债治理 | 行为保持、回归验证、目标技术债或质量结果得到证明 |
| 数据库迁移与架构迁移 | 兼容性、数据完整性、迁移顺序、前滚与回滚验证 |
| 依赖升级与安全修复 | 适用性分析、依赖或安全变更、回归与风险验证、遗留暴露说明 |
| 性能优化 | 可重复基线、可比优化后测量、正确性和非目标性能回归验证 |
| 发布与运维 | 制品与来源绑定、目标环境操作、健康验证、回滚准备和运行记录 |
| 线上事故响应 | 影响、遏制与恢复目标、服务恢复验证、残余风险和复盘证据 |

所有 Profile 都必须符合第 8 节标准产物和第 9 节安全底线。表中的差异是类别级
必要语义，不是九套独立引擎。

### 4.5 运行与集成边界

- 正式支持 macOS 和 Linux；Windows 原生不作 v1 兼容承诺，可通过 WSL 使用；
- 正式支持 Git，不支持其他版本控制系统；
- 对编程语言和技术栈保持中立，读取并遵循项目已有规范和工具链；
- 本地优先不等于完全离线；联网和数据外发必须透明并受权限与配置约束；
- Git 托管、CI、云、数据库和监控等能力通过命令、连接器或 adapter 接入；
- 不承诺穷举所有厂商集成；能力缺失必须明确标记为阻塞或未验证；
- 本地核心随 Skill 或其依赖安装，不要求用户部署或管理常驻服务。

## 5. 核心交付图

### 5.1 图节点

```text
Requirement Discovery [Human + Agent]
  → PRD Approval [Human]
  → Tech Spec Author ↔ Independent Reviewer
  → Impact Analysis Author ↔ Independent Reviewer
  → Implementation Plan / Test Plan ↔ Independent Reviewers
  → Implementation Loop ↔ Test / Review findings
  → Verification
  → Independent Candidate Review
  ├─ 无待执行的不可逆动作 → Completion Gate
  └─ 需要不可逆动作 → Human Action Approval
                       → Authorized Action Execution
                       → Target-state Verification
                       → Completion Gate
```

Positioning 仅在任务涉及新产品方向或现有定位改变时作为 Human-in-the-loop 上游
节点加入。Hotfix 与事故响应使用紧急 Intent Baseline，缩短 PRD 和计划，但不省略
目标、范围、权限、验证、回滚和证据。

### 5.2 图行为

- 节点是可执行 Agent Loop 或确定性控制节点，不是产物标签；
- 边声明 typed input/output、依赖、路由条件、信任和失效行为；
- Reviewer finding 按类型返回真正负责的上游节点；
- 常规 finding 自动修订并重新独立审核；
- 上游语义变化确定性地使受影响下游状态失效；
- 超过 loop budget、Reviewer 冲突或需改变意图时暂停并升级 Owner。

九类 Profile/子图在共享核心上声明各自的必需节点、可选节点、验证器、路由、回滚
和完成条件。完整计划、精简计划和紧急处置是风险路径，不替代具体任务类别；路径
由场景、风险和影响共同决定，不能以“精简”为由降低安全、验证或证据门槛。

## 6. 用户故事与验收

| ID | 用户故事 | 核心验收 |
|---|---|---|
| US-01 | 作为 Owner，我希望在 Codex 或 Hermes 中调用 Skill 并描述需求，以免部署工作流平台 | 任一 runtime 可独立创建任务；无需启动 daemon；Skill 自动读取项目规范和上下文；PRD 批准前对目标项目和外部资源只读 |
| US-02 | 作为 Owner，我希望 Agent 批量澄清关键问题，以便批准明确需求 | 只问无法可靠推断且实质影响结果的问题；形成目标、范围、非目标、约束和验收摘要；推荐场景 Profile 与风险路径 |
| US-03 | 作为 Owner，我希望明确批准当前 PRD 和初始权限边界，以便冻结 Agent 不能自行改变的意图与 Authority Envelope | 批准绑定当前内容和 digest；普通聊天不算批准；意图或权限语义变化必须重新批准 |
| US-04 | 作为 Owner，我希望批准后自动生成标准文档并开发，以免逐阶段协调 | Spec 至 Candidate Review 默认自主；常规 finding 自动回路；阶段产物满足质量契约 |
| US-05 | 作为 Owner，我希望系统只在必要时找我，以免“自动化”变成频繁确认 | 仅在意图变化、权限扩大、重大取舍、不收敛、外部阻塞或不可逆动作中断 |
| US-06 | 作为 Owner，我希望长任务保持意图一致，以免局部正确最终偏题 | 产物和证据绑定基线；偏离阻止传播；上游变化失效受影响下游 |
| US-07 | 作为 Owner，我希望任务只属于创建它的 runtime，以保持模型简单明确 | 任务记录 runtime 归属；另一 runtime 不能继续、批准或复用其授权 |
| US-08 | 作为 Owner，我希望关闭 runtime 后任务停止，再次打开时恢复 | 无 runtime 时没有后台推进；同 runtime 从本地状态恢复；不盲目重做不确定副作用 |
| US-09 | 作为 Owner，我希望对不可逆动作单独授权，以保留最终控制 | commit、push、merge、deploy、release，以及向当前任务会话之外发送的第三方或系统通信，分别绑定动作、资源、状态和有效期；授权后实际执行并验证结果 |
| US-10 | 作为 Owner，我希望完成摘要证明真实结果，以判断任务是否真正结束 | 目标状态、验收、项目验证、独立审核和证据全部有效；列明遗留、副作用和回滚状态 |
| US-11 | 作为 Owner，我希望紧急任务更快但仍安全，以处理 Hotfix 和事故 | 紧急基线至少包含影响、止损目标、权限、验证和回滚；生产动作仍需授权 |
| US-12 | 作为 Owner，我希望产品总结价值和反证，以共同寻找 PMF | 本地记录最小化介入、返工、耗时、失败、复用和放弃；方向变化由 Owner 批准 |
| US-13 | 作为 Owner，我希望九类软件工程任务都是真实完整支持，而不是理论可表达 | 每类具备 Profile/子图、类别级完成条件和冻结支持矩阵；全部必选场景通过后才能宣称支持 |
| US-14 | 作为 Owner，我希望并行任务和取消操作不会破坏共享资源 | 任务状态隔离；共享资源冲突在动作前检测；暂停、取消、撤权和回滚如实处理副作用 |
| US-15 | 作为 Owner，我希望 Skill 与本地状态可以安全升级 | 版本兼容可检查；升级前备份；迁移失败可恢复；进行中任务不会静默失效 |
| US-16 | 作为高级用户，我希望配置和扩展 Graph，以适配项目而不破坏安全底线 | 数据值位于配置；扩展声明契约并在加载前校验；底线只能收紧不能关闭 |
| US-17 | 作为 Owner，我希望状态与证据不会扩散秘密，以便安全审计任务 | 凭据只保存引用；证据最小化并脱敏；疑似泄露时隔离材料并生成不复述秘密的报告；向当前任务会话之外外发需授权 |

## 7. 功能需求

| ID | 优先级 | 需求 |
|---|---|---|
| FR-01 | Must | **Skill 入口：**Codex 与 Hermes 各自能完成创建、发现、批准、执行、恢复和结果查看；Hermes v1 支持 Telegram 与 Discord 入口 |
| FR-02 | Must | **任务归属：**任务永久绑定创建 runtime 与 Owner；其他人的输入不得改变任务状态、意图或授权；v1 不提供跨 runtime 接续或状态共享 |
| FR-03 | Must | **本地状态：**保存基线、图状态、权限、产物、证据和执行记录；runtime 重启后可恢复 |
| FR-04 | Must | **图执行：**支持专业 Loops、确定性节点、typed edges、条件路由、回退、汇合、重试和预算 |
| FR-05 | Must | **自动收敛：**常规失败和审核 finding 自动路由、修订、复验；必要边界才升级 Owner |
| FR-06 | Must | **意图保持：**基线、产物、证据和审核以 digest 绑定；语义变化失效受影响下游 |
| FR-07 | Must | **权限门禁：**PRD 批准前只允许写产品自身的候选文档与任务状态，对目标项目和外部资源只读；批准初始 Authority Envelope 后实施最小权限、动作级授权、状态绑定、过期失效及不可逆动作单独批准；runtime 在当前任务会话内回复 Owner 不视为额外外部通信 |
| FR-08 | Must | **中断恢复：**runtime 关闭即停止；恢复时协调进行中节点和未知副作用，不静默重复非幂等动作 |
| FR-09 | Must | **标准产物：**每阶段具备专业结构、状态、版本、输入基线、责任节点、审核和退出条件 |
| FR-10 | Must | **可信完成：**只有目标状态、验收、项目门槛、独立审核和有效证据全部通过才完成 |
| FR-11 | Must | **隐私证据：**本地、最小化、脱敏；秘密只存 provider 引用，不进入 Graph State 或证据；疑似泄露时隔离并生成不复述秘密的报告；向当前任务会话之外外发证据或数据需授权 |
| FR-12 | Must | **配置与数据分离：**项目、环境、命令、阈值和图策略位于配置；提供可靠默认值；配置不能降低安全底线 |
| FR-13 | Must | **产品学习：**本地形成最小 PMF 记录，Agent 主动提出假设、反证和实验建议 |
| FR-14 | Must | **场景 Profile：**九类任务分别声明必需/可选节点、路由、产物、验证器、回滚和完成条件，并通过版本化支持矩阵验收 |
| FR-15 | Must | **项目与任务生命周期：**稳定任务 ID；支持创建、列出、搜索、查看，以及新建/既有、多仓库/服务/环境；可暂停、取消、撤权、归档和受控回滚；动作前检测共享资源冲突 |
| FR-16 | Must | **安装与升级：**macOS/Linux 本地安装、初始化、备份、核心/Skill/状态版本迁移及迁移失败恢复 |
| FR-17 | Must | **真实操作：**在有效授权内通过命令、连接器或 adapter 操作仓库、交付系统和目标环境；把动作结果与当前状态绑定，失败时停止、协调或按授权回滚，并验证目标状态 |
| FR-18 | Should | **高级扩展：**本地加载节点、边、策略、模板和 adapter；声明输入输出、权限、副作用、失败和验证契约；加载前校验 |

## 8. 标准阶段产物

“标准”表示满足对应专业阶段的决策和追踪目的，不要求固定篇幅。

| 阶段 | 最低内容 |
|---|---|
| Positioning（按需） | 市场背景、用户、问题、类别、价值、替代方案、差异化、边界、成功假设、定位陈述、批准状态 |
| PRD | 用户/JTBD、目标、范围、User Stories、验收、风险依赖、追踪、批准状态 |
| Tech Spec | 架构、组件、状态与数据、接口、流程、安全、可靠性、迁移回滚、替代方案、追踪 |
| Impact Analysis | 受影响模块/用户/数据/依赖、兼容性、安全、运行影响、风险和 ADR 判断 |
| Plan | 工作分解、依赖、责任节点、交付物、风险、检查点、退出条件和需求映射 |
| Test Plan | 策略、追踪、环境、正常/边界/失败/恢复/安全场景、通过标准和证据 |
| Implementation | 符合项目规范的代码、配置、迁移和必要文档；不夹带未批准范围 |
| Verification | 构建、测试、静态/安全/性能检查、目标状态、证据、偏差和残余风险 |
| Candidate Review | 独立 Reviewer、逐项需求结论、finding、意图与证据完整性、交付建议 |
| Completion Record | 实际变化、目标状态、授权、副作用、回滚、遗留事项和审计入口 |

风险较低或紧急任务可合并或缩短产物，但不能删除意图、权限、验证、独立审核、
证据和需求追踪底线。内部运行日志不能冒充正式产物。

## 9. 确定性安全底线

以下能力不能由 LLM、Skill 指令、配置或 runtime adapter 绕过：

- Authority Envelope 和动作级权限校验；
- Intent Baseline、状态、产物、证据和审核的 digest 绑定；
- schema 校验、状态转换、边条件、loop budget 和不可逆门禁；
- 上游语义变化触发的下游失效；
- 非幂等副作用的重放保护；
- 阶段退出、目标状态和证据有效性判定。

这些能力可以由 Skill 调用的本地脚本或库实现，但不能只依赖提示词要求 Agent
自觉遵守。

## 10. 非功能需求

| ID | 要求 |
|---|---|
| NFR-01 简单性 | 普通用户只需安装/调用 Skill，不需要部署或管理 daemon、数据库服务或工作流平台 |
| NFR-02 可靠性 | 无法证明完成时保持未完成，并给出阻塞、继续或回滚路径 |
| NFR-03 可恢复性 | 同 runtime 恢复不丢失基线、权限、历史和证据，不重复不确定副作用 |
| NFR-04 平台中立 | 通用图和安全语义不依赖 Codex 或 Hermes；runtime 只通过 adapter 接入 |
| NFR-05 数据逻辑分离 | 图、策略、阈值、命令、路径和环境值来自配置或数据，不写死在引擎逻辑 |
| NFR-06 隐私 | 本地控制、最小权限、最小留存、透明外发和秘密引用化 |
| NFR-07 可审计性 | 从批准意图到最终结果可追踪、可重放，证据不可跨任务或基线串用 |
| NFR-08 兼容性 | 遵循既有项目规范与工具链；能力或版本不兼容时明确失败，不虚假降级 |

## 11. 依赖、约束与风险

### 11.1 依赖与约束

- 用户环境中具有 Git、本地文件系统、Shell 和目标项目需要的工程工具；
- 至少安装 Codex Skill 或 Hermes Skill 其中一个完整入口及其本地核心依赖；
- 外部操作依赖相应命令、连接器、凭据、网络和 Owner 授权；
- runtime 关闭后没有进程代表产品继续推进任务；
- 旧项目只作只读背景参考，不能修改或成为运行时依赖。

### 11.2 主要风险

| 风险 | 缓解要求 |
|---|---|
| 九类范围仍然过宽 | 冻结逐类支持矩阵；未全部通过的类别不得宣称支持 |
| 共享核心掩盖类别缺口 | 每类独立定义 Profile、完成语义和真实端到端验证 |
| Skill 指令被误当作安全内核 | 权限、状态、digest、预算和完成门禁由确定性本地核心执行 |
| runtime 关闭造成未知副作用 | 安全检查点、动作意图记录、幂等键和恢复协调 |
| 单 runtime 归属限制使用体验 | 明确拒绝跨 runtime；用真实使用证据验证该取舍 |
| 标准产物产生形式主义 | 风险相称地合并或缩短，以决策、证据和追踪质量验收 |
| 敏感数据进入状态或证据 | 秘密引用化、最小留存、脱敏、隔离和不复述秘密的报告 |
| 技术完成但没有 PMF | 真实任务、自用、持续复用和主动反证机制 |

## 12. v1 发布门槛

v1 使用一份冻结的九类支持矩阵。共享核心减少重复实现，但每类任务的产品承诺
必须独立、完整地通过矩阵，不能以其他类别或通用框架通过代替。

### 12.1 九类支持矩阵

每类 Profile/子图都必须通过：

- 内置端到端正常路径；
- 该类别的关键边界和类别级完成语义；
- 失败后的自动修订与重新验证；
- 权限拒绝、过期和 digest 失配；
- 意图漂移检测及下游失效；
- runtime 中断、同 runtime 恢复和未知副作用协调；
- 标准阶段产物、独立审核、Candidate Review 和目标状态验证；
- 至少一个真实项目、真实工具链的端到端场景。

冻结矩阵中的全部必选场景和验收条件必须通过，不得在发布时临时缩小矩阵。未经
验证的技术栈或厂商集成必须明确标记，但不能用这种标记掩盖类别核心路径未完成。

### 12.2 Runtime 与风险模式

- Codex Skill 与 Hermes Skill 必须通过同一 runtime adapter 契约测试；
- Hermes 的 Telegram 与 Discord 渠道分别通过创建、Owner 身份、批准、恢复和结果
  查看契约测试；
- 每个 runtime 都必须完整完成至少一项完整计划、精简计划和紧急处置任务；
- runtime 中断后，同一 runtime 能恢复并继续；
- 另一 runtime 尝试接续时被明确拒绝，不复用状态或授权。

九类支持矩阵的真实任务可以同时用于满足 runtime 和风险模式门槛，但不得减少九类
逐项验收覆盖。

### 12.3 可靠性与安全

- 常规 finding 能自动回到责任节点并收敛；
- 意图变化会停止传播、请求批准并失效受影响下游；
- 未授权或 digest 不匹配的动作全部被阻止；
- runtime 关闭后不存在后台推进；
- 恢复不重复非幂等副作用；
- 无效或跨任务证据不能用于完成判定；
- 最终摘要证明目标状态而非只罗列产物。

### 12.4 产品体验

- Owner 可仅用自然语言启动；
- 问题优先批量提出；
- PRD 批准后，常规阶段不再要求 Owner 逐步确认；
- 每次升级包含问题、证据、选项、推荐和明确决定点；
- 普通用户无需理解 Graph 内部或管理后台服务。

## 14. 留给 Tech Spec 的决策

- Skill 的目录、打包和 Codex/Hermes 适配方式；
- 本地任务目录、状态、artifact、authority 和 evidence schema；
- 无 daemon 条件下的锁、事务、恢复和幂等策略；
- Graph 配置、typed edge 和 finding taxonomy；
- 九类 Profile/子图及版本化支持矩阵的 schema；
- Reviewer 隔离、预算和收敛算法；
- 项目命令、secret provider 和外部工具适配契约；
- 完整计划、精简计划和紧急处置路径的具体模板和节点组合。

技术选择不得重新引入后台运行或跨 runtime 共享，也不得缩小本文的意图、安全和
验收边界。

## 15. Intent Baseline v2 摘要

1. 产品采用本地优先确定性核心，以 Codex/Hermes Skill 为主要入口，不要求常驻服务；
2. 每个任务只属于一个 runtime 和一位 Owner；
3. runtime 关闭即暂停，同一 runtime 可从本地状态恢复；
4. v1 不支持后台持续执行、跨 runtime 接续或自动事件监听；
5. 共享确定性核心承载九类完整 Profile/子图；九类支持矩阵必须全部通过；
6. 通过完整计划、精简计划和紧急处置三条路径实现风险相称交付，但不降低安全底线；
7. PRD 批准后，标准文档、实现、验证和审核默认自主完成；
8. 只在意图、权限、重大取舍、不收敛、外部阻塞和不可逆动作时找 Owner；
9. 确定性逻辑防止意图漂移、越权、无效状态和证据串用；
10. 系统在有效授权后实际执行所需操作，并以真实目标状态、独立审核和完整证据结束；
11. Human 与 Agent 共同检验 PMF，方向变化仍由 Owner 批准。
